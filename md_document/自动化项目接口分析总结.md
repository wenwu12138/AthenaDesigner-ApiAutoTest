# AthenaDesigner-ApiAutoTest 接口分析总结

## 1. 项目概况

该项目是一个基于 `pytest + YAML 用例 + Python 请求封装` 的接口自动化项目。

核心特点：

- 用例源数据存放在 `data/` 目录下的 YAML 文件中
- `test_case/` 中的 Python 测试代码负责调度执行
- 请求发送由统一封装层处理
- 断言、依赖、缓存、后置请求、SQL 校验都通过统一字段规范驱动
- 项目内已经存在基于 OpenAPI 契约文件的接口覆盖率统计能力

关键目录：

- `data/`：接口 YAML 用例
- `test_case/`：pytest 测试文件
- `utils/requests_tool/`：请求执行与依赖处理
- `utils/read_files_tools/`：YAML 解析、模板生成、Swagger 转 YAML
- `utils/other_tools/InterfaceCoverage.py`：接口覆盖率统计
- `data/ServerApi.json`：当前用于统计覆盖率的后端接口契约快照

## 3. 当前已覆盖接口数、覆盖率

### 3.1 统计口径

当前覆盖率基于以下规则计算：

- 后端接口全集来源：`data/ServerApi.json`
- 统计对象：OpenAPI 中的 `GET / POST / PUT / DELETE / PATCH`
- `actuator` 接口不计入
- 自动化覆盖来源：`data/*.yaml` 中每个用例的 `url + method`
- 覆盖判断：YAML 中的接口与 `ServerApi.json` 中的接口完全匹配

### 3.2 统计结果

- YAML 文件总数：`28`
- YAML 用例总数：`438`
- YAML 中唯一接口数：`229`
- 与契约匹配的已覆盖唯一接口数：`181`
- 契约总接口数：`1802`
- 当前接口覆盖率：`10.04%`
- 未覆盖接口数：`1621`

### 3.3 额外观察

- YAML 中共有 `229` 个唯一接口，但只有 `181` 个与 `ServerApi.json` 成功匹配
- 说明存在 `48` 个接口属于以下情况之一：
  - 契约文件已过期，和当前自动化用例不一致
  - 用例 URL 与契约 URL 存在路径差异
  - 自动化项目覆盖了契约外接口
  - 契约中接口前缀 / 路径规则发生过变化

因此，当前 `10.04%` 是“按当前契约快照计算的有效覆盖率”，这个口径是后续扩大覆盖率时应继续沿用的正式口径。

## 4. 当前自动化项目的接口规范

该项目的接口规范是 YAML 驱动，不是直接在 Python 测试里硬编码请求。

### 4.1 YAML 顶层结构

每个 YAML 文件包含：

- `case_common`：公共 Allure 信息
- 多个 `case_id`：具体接口测试用例

示例结构：

```yaml
case_common:
  allureEpic: xxx
  allureFeature: xxx
  allureStory: xxx

action_FindActionsNoPaging_001:
  host: ${{athena_designer_host()}}
  url: /athena-designer/action/findActionsNoPagingV2
  method: GET
  detail: 查询Actions列表（无分页）
  headers:
    digi-middleware-auth-user: $cache{token}
    token: $cache{token}
    locale: zh_CN
  requestType: PARAMS
  is_run: true
  data:
    labelType: ""
    condition: ""
    appCode: ${{app2_code()}}
  dependence_case: false
  dependence_case_data:
  assert:
    code:
      jsonpath: $.code
      type: ==
      value: 0
      AssertType:
```

参考文件：

- [data/Application2.0_Businessconstruction/Action.yaml](D:/sort/AthenaDesigner-ApiAutoTest/data/Application2.0_Businessconstruction/Action.yaml)

### 4.2 规范字段

根据项目字段模型，标准用例核心字段如下：

### 4.3 请求类型规范

对应请求发送逻辑见：

### 4.4 断言规范

当前断言以 `assert` 字段驱动，支持通过 `jsonpath` 取值后比较。

常见断言形态：

```yaml
assert:
  code:
    jsonpath: $.code
    type: ==
    value: 0
    AssertType:
```

也支持更复杂的断言类型、SQL 断言、异步断言、后置动作断言。

### 4.5 依赖与缓存规范

当前框架支持：

- 接口依赖前置用例结果
- 从响应体提取字段写入缓存
- 后续请求通过 `$cache{xxx}` 引用
- 支持 `current_request_set_cache`

示例：

```yaml
current_request_set_cache:
  - type: response
    jsonpath: $.data.actionId
    name: action_id
```

### 4.6 用例生成规范来源

项目内已经有“从 Swagger/OpenAPI 生成 YAML 初始用例”的实现：

- [swagger_for_yaml.py](D:/sort/AthenaDesigner-ApiAutoTest/utils/read_files_tools/swagger_for_yaml.py)

当前生成逻辑特点：

- 从 OpenAPI `paths` 生成 YAML
- 自动生成 `case_common`
- 自动生成：
  - `host`
  - `url`
  - `method`
  - `detail`
  - `headers`
  - `requestType`
  - `data`
  - 默认断言
- 生成结果是“可执行基础壳子”，后续仍需人工或程序补充：
  - token/header
  - 动态参数
  - 业务依赖
  - 缓存提取
  - 更细断言

## 5. Python 测试执行规范

项目执行链路是：

1. 扫描 `data/` 下所有 YAML
2. 将用例写入缓存池
3. `test_case/*.py` 通过 `GetTestCase.case_data(case_id)` 读取用例
4. `RequestControl` 统一发请求
5. 断言、缓存、依赖、后置逻辑统一执行

关键文件：

- [test_case/__init__.py](D:/sort/AthenaDesigner-ApiAutoTest/test_case/__init__.py)
- [testcase_template.py](D:/sort/AthenaDesigner-ApiAutoTest/utils/read_files_tools/testcase_template.py)

说明：

- 这个项目是“YAML 驱动 + Python 模板承载执行”
- 所以后续自动生成接口用例时，应优先生成 YAML，用现有 Python 模板执行
- 不建议跳过现有规范直接新建独立风格的 pytest 文件

## 7. 当前项目存在的接口覆盖问题

### 7.1 覆盖率偏低

- 当前契约总接口 `1802`
- 有效覆盖唯一接口仅 `181`
- 覆盖率仅 `10.04%`

这意味着主干业务之外，还有大量接口未纳入自动化。

### 7.2 契约与用例存在不一致

- YAML 唯一接口数 `229`
- 有效匹配接口数 `181`

说明契约文件与测试用例之间存在一定漂移。

### 7.3 当前更偏“重点业务回归”，不是“全量契约覆盖”

现有项目适合回归核心路径，但如果后续目标是“扩大覆盖率”，就必须改为：

- 先基于后端契约生成可执行 YAML 壳子
- 再按现有规范补全参数、依赖、断言
- 最终逐步提升契约覆盖率

## 8. 后续自动生成接口用例时应遵守的规则

后续我如果基于后端项目接口自动生成用例，应遵守以下规则：

1. 生成目标优先是 `data/` 下 YAML 文件，不是直接手写 pytest 逻辑
2. 按现有业务目录分类落盘
3. 每个 YAML 文件保留：
   - `case_common`
   - 多个 `case_id`
4. 每个 case 至少生成以下字段：
   - `host`
   - `url`
   - `method`
   - `detail`
   - `headers`
   - `requestType`
   - `is_run`
   - `data`
   - `dependence_case`
   - `assert`
5. 默认断言先生成基础成功断言：
   - HTTP 成功
   - `$.code == 0` 或项目统一成功码
6. 对需要前置数据的接口，再自动补：
   - `current_request_set_cache`
   - `dependence_case_data`
7. 自动生成时必须优先复用现有模块命名和文件拆分方式
8. 统计覆盖率时继续沿用 `ServerApi.json` 作为基准契约

## 9. 结论

这个自动化项目已经具备继续扩张覆盖率的基础能力：

- 有统一 YAML 规范
- 有统一请求执行器
- 有断言与依赖机制
- 有从 OpenAPI 到 YAML 的生成基础
- 有现成的覆盖率统计逻辑

当前最大问题不是“没有框架”，而是：

- 覆盖率低
- 契约与用例有漂移
- 还有大量接口未进入自动化

因此，后续最合理的路线是：

1. 以 `athena_designer` 后端接口契约为全集
2. 以本项目当前 YAML 规范为生成规范
3. 自动生成新的 YAML 用例骨架
4. 按业务模块逐批补充参数、依赖、断言
5. 持续提升覆盖率
