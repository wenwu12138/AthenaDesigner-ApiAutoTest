# 后端接口用例文档规范

更新时间：2026-04-09

## 1. 文档定位

本文档用于定义“基于后端项目生成接口用例文档”的统一规范。

这份文档的目标不是直接生成 `data/ai` 下的 YAML，而是先在后端源码与自动化 YAML 之间增加一层稳定的中间产物：

- 对人可读：方便审阅、补充、纠偏
- 对机器可读：方便后续继续生成自动化配置用例
- 对规则可控：把“接口事实”和“测试设计”从一开始就分离清楚

统一链路如下：

1. 扫描后端项目源码
2. 生成接口用例文档
3. 基于接口用例文档生成自动化 YAML
4. 执行 `case_automatic_control.py` 和 pytest 自检

## 2. 文档存放规则

- 所有文档统一存放在：`D:\sort\AthenaDesigner-ApiAutoTest\md_document`
- 后续基于后端生成的接口用例文档，也统一放在该目录下
- 不在后端项目 `D:\sort\athena_designer` 内落测试设计文档

推荐命名规则：

- 总规范：`后端接口用例文档规范.md`
- 模块级接口用例文档：`{模块名}接口用例文档.md`
- 全量汇总文档：`athena_designer接口用例总表.md`
- 结构化机读文件：`athena_designer接口用例总表.json`

## 3. 生成目标

接口用例文档不是单纯接口清单，而是“可继续生成自动化 YAML”的设计文档。

每个接口在文档中至少要回答下面 8 个问题：

1. 它是什么接口
2. 它的真实请求结构是什么
3. 它依赖哪些认证或特殊请求头
4. 它是否依赖真实前置实体
5. 它适合生成哪类用例
6. 它是否能进入稳定集
7. 它建议放进哪个 `data/ai` 业务域 YAML
8. 它后续生成 YAML 时需要哪些缓存链、断言和注意事项

## 4. 文档分层

后续建议同时维护两层产物。

### 4.1 人读文档

格式：Markdown  
用途：人工评审、补充规则、沉淀业务语义、确认边界

建议文件：

- `athena_designer接口用例总表.md`
- `application接口用例文档.md`
- `pagedesign接口用例文档.md`

### 4.2 机读文档

格式：JSON 或 YAML  
用途：后续自动生成 `data/ai` 用例时直接消费

建议文件：

- `athena_designer接口用例总表.json`

原则：

- Markdown 负责“解释”
- JSON/YAML 负责“结构化字段”
- 两者应尽量同源生成，避免维护两套内容

## 5. 接口分级规则

后续生成接口用例文档时，每个接口都要先分级。

### 5.1 A 类：可直接进入首批稳定集

特点：

- Controller 参数明确
- 最小请求体清晰
- 不依赖真实已有实体，或依赖可由前置新增稳定生成
- 不强依赖复杂权限或外部系统

### 5.2 B 类：需要补规则后再生成

特点：

- query + body 混合
- 数组 body、泛型 body、嵌套 DTO 较复杂
- 需要额外请求头
- 需要简单缓存链才能稳定运行

### 5.3 C 类：暂不进入通用稳定集

特点：

- 强依赖真实 `id/code/processId/taskCode/pageCode`
- 强依赖授权、租户、角色、应用关系
- 强依赖文件、导入导出、第三方服务、异步处理
- 当前环境无法稳定构造前置链路

## 6. 接口用例文档标准字段

后续无论是 Markdown 还是 JSON，字段语义都按本节统一。

### 6.1 基础标识字段

- `module`
  - 所属模块，如 `application`、`pagedesign`、`agiledatainquiry`
- `controller`
  - Controller 类名
- `method_name`
  - Java 方法名
- `http_method`
  - `GET / POST / PUT / DELETE / PATCH`
- `url`
  - 完整接口路径，统一带 `/athena-designer`
- `summary`
  - 接口简要说明

### 6.2 后端结构字段

- `class_mapping`
  - 类级别 `@RequestMapping`
- `method_mapping`
  - 方法级别映射
- `request_headers`
  - 显式声明的请求头要求
- `path_params`
  - 路径参数摘要
- `query_params`
  - 查询参数摘要
- `body_type`
  - 请求体类型，如 `none`、`object`、`array`
- `body_class`
  - DTO 类名或集合元素类型
- `body_fields`
  - 请求体关键字段摘要
- `response_wrapper`
  - 是否为 `ResultBean`
- `response_data_path`
  - 主要数据路径，如 `$.data`、`$.dataList`

### 6.3 自动化判定字段

- `auth_required`
  - 是否需要登录态
- `special_headers`
  - 是否需要 `Authorization` 等特殊头
- `case_level`
  - `A / B / C`
- `case_type`
  - `query / create / update / delete / chain / export / import`
- `business_domain`
  - 应并入哪个 `data/ai/ai_业务域.yaml`
- `priority`
  - `P1 / P2 / P3`

### 6.4 前置依赖字段

- `requires_existing_entity`
  - 是否依赖真实已存在实体
- `precondition_source`
  - 前置实体来源
  - 可选值示例：`none`、`create_in_chain`、`query_existing`、`manual_env`
- `recommended_chain`
  - 推荐闭环名称
- `cache_strategy`
  - 推荐缓存策略
- `cache_fields`
  - 建议缓存哪些字段，如 `code`、`id`、`objectId`

### 6.5 断言设计字段

- `base_assertions`
  - 基础断言，至少含 `$.code == 0`
- `business_assertions`
  - 建议业务断言
- `post_check`
  - 是否建议写后查、删后查、恢复后查
- `reversible`
  - 是否适合做可逆闭环

### 6.6 风险与说明字段

- `risk_notes`
  - 风险说明
- `skip_reason`
  - 若当前不建议生成，明确原因
- `remarks`
  - 其他补充说明

## 9. 生成原则

### 9.1 先提取接口事实，再写测试设计

接口用例文档必须区分两类信息：

- 后端源码客观事实
- 自动化测试设计判断

禁止把推测内容伪装成后端事实。

### 9.2 DTO 结构不能只看接口名猜

凡是请求体不是简单扁平对象时，必须结合：

- Controller 方法签名
- DTO 字段
- Service 实际消费字段

只看 `createOrUpdate`、`save`、`grantAuth` 这类名字不够。

### 9.3 编辑、删除类接口优先视为链路节点

若接口依赖真实实体，则文档里不能把它标记为“可独立稳定生成”。

必须明确：

- 它依赖什么实体
- 这个实体从哪里来
- 是否需要前置新增或前置查询

### 9.4 断言不能长期停留在 `code == 0`

文档中可以先保留基础断言，但应尽量补：

- 主键/编码一致性
- 列表非空
- 详情字段存在
- 状态变更前后差异
- 删除后查询为空

### 9.5 优先设计可逆闭环

涉及状态、配置、开关、绑定关系的接口，优先设计：

1. 查询当前值
2. 修改
3. 再查确认
4. 恢复
5. 最终确认恢复

## 10. 与自动化 YAML 的映射关系

接口用例文档的目标之一，是为后续生成 `data/ai` 下 YAML 提供映射依据。

映射示例：

- `http_method` -> `method`
- `url` -> `url`
- `special_headers` -> `headers` 补充项
- `body_type` + `query_params` -> `requestType`
- `business_domain` -> 目标 YAML 文件
- `cache_fields` -> `current_request_set_cache`
- `base_assertions` + `business_assertions` -> `assert`
- `recommended_chain` -> `allureStory` 和 case 组织依据

说明：

- 接口用例文档不直接等同 YAML
- 它提供的是“生成 YAML 所需的上下文和设计信息”

## 11. 第一批落地建议

首批建议不要全量扫描 181 个 Controller 后一次性产出全部文档，而是先做试点模块。

推荐顺序：

1. `agiledatainquiry`
2. `application`
3. `pagedesign`
4. `activity / message`

每个试点模块先产出两份内容：

- 一份 Markdown 接口用例文档
- 一份 JSON 结构化接口清单

验证点：

- 能否正确识别请求参数结构
- 能否正确判断 A/B/C 类
- 能否正确归到 `data/ai` 的业务域
- 能否据此稳定生成一批 YAML
